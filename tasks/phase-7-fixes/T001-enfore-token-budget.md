# T001: Enforce Aggregate Token Budgets for Experiment Arms

## Goal

Make `total_token_budget` an execution limit, not an analysis-only allocation,
for every fixed-budget experiment arm. A branch arm must spend no more than its
configured aggregate budget across its root and all executed continuations.
This makes clean-retry and checkpoint/restore results comparable at the same
test-time-compute budget.

## Context

`go_explore.fixed_budget` currently labels budgets as `planning_only`; Harbor
and the wrapped agent are not stopped at the assigned amount. As a result, a
child continuation can consume far more tokens than its allocation and make a
branch solve look cheaper than an equivalent clean-retry arm. Phase 6 recorded
this explicitly: a build-cython retry used about 9.16M tokens despite a much
smaller planned allocation.

The desired comparison is:

- clean retry: `N` independent jobs whose enforced limits sum to `B`;
- branch: one root plus its executed continuation jobs whose enforced limits
  sum to `B`.

The root is allowed to fail. A child may use only its allocated share; it must
not receive an unbounded budget just because it restores a useful checkpoint.
This ticket is about budget enforcement and accounting, not about improving
snapshot selection or supplying parent reasoning to children.

## Scope

1. Identify the narrowest supported Harbor/Terminus-2 or model-client control
   that can stop further model work at a per-job token limit. Confirm it with
   a local unit/integration seam; do not assume a CLI argument is enforced.
2. Thread each `PlannedExperimentJob.budget.token_budget` into that execution
   control for `single`, every retry attempt, every branch root, and every
   continuation.
3. Preserve the existing deterministic allocation policy: the per-job limits
   for a method and seed must add up exactly to `total_token_budget` (subject
   to the existing one-token remainder distribution).
4. Make continuation execution use the planned child allocation rather than
   reconstructing unrestricted Harbor commands from the root config.
5. Record enough information to audit enforcement in the manifest, execution
   report, continuation report, and analysis output:
   - requested/enforced token limit for each job;
   - enforcement mode and mechanism/version, if available;
   - observed total tokens and their completeness status;
   - whether the job stopped because its budget was exhausted.
6. Replace the global `planning_only` label only when the selected mechanism
   genuinely prevents additional model requests after the limit. If a strict
   cap cannot be implemented with the available Harbor/agent API, retain
   `planning_only`, emit an explicit unsupported-enforcement warning, and
   document the blocking upstream capability. Do not present this fallback as
   a fixed-budget result.
7. Keep all existing non-budget agent behavior unchanged: snapshot creation,
   restore, selector choice, context mode, and replay behavior are not part of
   this ticket.

## Out of Scope

- Changing the root/child budget split or choosing an adaptive allocation.
- Dynamic reallocation of unused root budget to children. This can be a later
  experiment policy once the hard-cap baseline is trusted.
- Selector improvements, stage-aware snapshotting, diversity metrics, or
  parent-summary prompt design.
- Retrofitting historical `planning_only` runs to appear enforced.
- Enforcing dollar or wall-clock budgets; record them as today but do not
  conflate them with token enforcement.

## Suggested Starting Points

- Inspect the installed Harbor and Terminus-2 APIs for a per-run or per-agent
  token/cost limit. Prefer a documented API or agent kwarg over parsing output
  or killing a subprocess after the fact.
- Trace command construction through `go_explore.harbor.build_harbor_command`,
  `_run_planned_job`, `plan_snapshot_continuations`, and
  `run_continuation_plans`.
- Inspect token extraction in `go_explore.results.summarize_job` and the
  analysis warnings generated by `go_explore.analysis_tables`.
- Read the fixed-budget tests in `tests/test_continuations.py`,
  `tests/test_experiment_runner.py`, and `tests/test_analysis_tables.py`.

## Implementation Guidance

- Model enforcement as a small, explicit configuration value (for example,
  `budget_enforcement="hard_token_limit"`), not a Boolean spread through the
  runner. Keep the mechanism-specific translation isolated at the Harbor/agent
  boundary.
- A continuation plan needs its own enforced allocation. Do not let it inherit
  the root's limit or a default unlimited limit.
- Token totals are generally available only after a request completes. The
  implementation should prevent *starting another* request when the remaining
  budget cannot cover it, and use any provider-supported request cap to bound
  the final request. Clearly document any unavoidable bounded overshoot and
  expose it in reports; do not silently call it exact enforcement.
- Do not inject budget details into the parent context or tell the child that
  the parent's solution is correct. If the underlying agent supports a neutral
  remaining-budget instruction, keep it factual and independent of parent
  reasoning.
- Follow repository conventions: frozen dataclasses for immutable planning
  records, small helpers with single responsibilities, typed public APIs, and
  focused docstrings for non-obvious behavior. Avoid broad exception handling
  and avoid duplicating Harbor command construction.
- Update user-facing documentation that currently states `planning_only`.

## Acceptance Criteria

- A fixed-budget manifest distinguishes enforced budgets from legacy
  `planning_only` plans and serializes the per-job token limit and enforcement
  metadata.
- For each method/seed with a total budget `B`, the planned limits sum to `B`:
  `single == B`, retries sum to `B`, and branch root plus all planned children
  sum to `B`.
- The actual launch path passes the appropriate limit to every ready Harbor
  job, including continuations created after a root archive is selected.
- A job that exhausts its limit ends with a machine-readable
  `budget_exhausted` termination/enforcement status rather than continuing
  unbounded. A normal completion before the limit remains distinguishable.
- Execution and continuation reports include the requested limit, enforcement
  status, observed token total/status, and any bounded overshoot.
- Analysis tables warn on missing or partial token accounting and on observed
  overshoot. They must not label an arm as a valid equal-budget comparison when
  enforcement or complete accounting is absent.
- Existing manifests and result directories remain readable. They continue to
  be reported as `planning_only` rather than being reinterpreted.
- `uv run pytest -q` passes.

## Test Coverage

- Unit-test manifest planning and JSON round trips for both legacy
  `planning_only` and enforced modes.
- Unit-test command/config translation: each role receives its own exact token
  limit; branch child commands do not reuse the root limit.
- Unit-test budget splitting with indivisible totals and assert exact aggregate
  sums for every method.
- Unit-test the execution adapter with a fake agent/client that consumes tokens
  across multiple requests. Verify it stops before an additional request,
  reports `budget_exhausted`, and records a normal early completion correctly.
- Unit-test continuation execution with two children to verify their individual
  caps and the root-plus-children aggregate cap.
- Unit-test analysis for complete accounting, missing accounting, and an
  overshoot/unsupported-enforcement case.
- Add a small integration test only if the installed Harbor API exposes a
  deterministic local fake or dry-run surface. Do not spend model credits in
  the default suite. Mark any live Harbor/Daytona verification as E2E.

sum exactly, the generated continuation command contains the child limit, and
the resulting execution/analysis reports expose enforcement rather than the
old `planning_only` label.

## Notes / Open Questions

- Determine whether the available provider reports input, output, and cache
  tokens before a next request can be admitted. Cache accounting may make a
  mathematically exact hard cap impossible without upstream support; document
  the guarantee precisely.
- If Harbor offers only a timeout or max-turn control, it is not token-budget
  enforcement. Keep the ticket blocked on a real control rather than shipping a
  mislabeled approximation.
- A future ticket may safely redistribute unused root allocation after its
  final usage is known. Keep that policy separate so this change establishes a
  stable, reproducible baseline first.
